## 2. Compatibilité

Ce qui ne doit pas bouger d'un octet, et le test qui le garde :

- le format `dsh-v1`, son vecteur (`docs/dataset-hash.md` §7) et les hashes épinglés de `fixtures/golden/` (`tv4/tests/store.rs`) : `block` n'entre pas dans le flux haché (§6.1) ;
- les goldens de run `sma_cross_15m_okx`, `sma_cross_1m_court_okx`, `portfolio_2legs` et `portfolio_profiles`, les snapshots insta, les chaînes canoniques épinglées de `RunConfig` (`00fbee51…`) et de `PortfolioRunConfig` v1 (`36bd64fd…`) et v2 ;
- les manifestes de dataset existants (`btcusd_2y`, `fumee_duo`, ceux du Mac) : ils n'ont pas `block`, se relisent sans erreur et ne sont jamais réécrits (§6.2) ;
- les rapports s8, s9 et s10 et les fixtures PHP `run-exemple`, `run-portefeuille`, `run-profils`, `rapport-s8-attendu.html`, `rapport-s9-attendu.html`.

Garde-fou des goldens existants : `portfolio_2legs` et `portfolio_profiles` sont joués par la CLI (`tests/golden_run_portfolio.rs`, `tests/cli_portfolio.rs`) sur des datasets synthétiques datés de janvier 2024 (`tests/report_s9_common/mod.rs` l.17-18 et l.66, fenêtre à partir de `T0` = 2024-01-01, dans VALIDATION ; même `T0` dans `tests/portfolio_common/mod.rs` l.18-19), et `tests/cli_profiles.rs` l.424 date ses mesures de novembre 2023. Aucune règle de S11 ne doit donc refuser un dataset **sans** `block` à cause de sa date (§9.5).

Règle : **un dataset sans `block` ne déclenche jamais le mode recherche**. Toute option de S11 (`--universe`, `--okx-subset`) sur un tel dataset est refusée (code 2). Un dataset avec `block` ne se joue qu'en mode recherche, et seulement en mode portefeuille (§8.1). Le mode recherche a sa propre génération de schémas (s11) : un lecteur qui ne connaît pas s11 refuse le run au lieu d'afficher des métriques purgées comme si elles ne l'étaient pas.

## 3. Blocs, embargos, chauffe et purge (point 4)

### 3.1 Type et constantes (`model/blocks.rs`, nouveau)

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord, Serialize, Deserialize)]
#[serde(rename_all = "SCREAMING_SNAKE_CASE")]
pub enum Block { Dev, Validation, Holdout, Forward }

pub struct BlockSpan { pub start_ms: Ts, pub end_ms: Option<Ts> }   // [start, end), None = ouvert à droite

pub const BLOCKS: [(Block, BlockSpan); 4];      // ordre chronologique
pub const EMBARGOS: [(Ts, Ts); 2];               // [début, fin) de chaque embargo
pub const WARMUP_PREFIX_DAYS_DEFAULT: i64 = 210; // §3.3
pub const BLOCKS_VERSION: &str = "b1";           // entre dans le config_hash (§8.6)
```

| Élément | Dates de 04 §2.3 | `[start_ms, end_ms)` |
|---|---|---|
| DEV | 2018-01-01 → 2022-12-31 | `[1514764800000, 1672531200000)` |
| Embargo 1 | 2023-01-01 → 2023-02-28 | `[1672531200000, 1677628800000)` |
| VALIDATION | 2023-03-01 → 2024-12-31 | `[1677628800000, 1735689600000)` |
| Embargo 2 | 2025-01-01 → 2025-02-28 | `[1735689600000, 1740787200000)` |
| HOLDOUT | 2025-03-01 → 2026-06-30 | `[1740787200000, 1782864000000)` |
| FORWARD | 2026-07-01 → … | `[1782864000000, ∞)` |

Les dates de 04 sont inclusives ; les intervalles du code sont semi-ouverts, fin au lendemain 00:00 UTC. Valeurs calculées pour cette spécification et recalculées par le test du lot A à partir de `store::time::days_from_civil` (`store/time.rs` l.25) : `model` ne dépend de rien et ne peut pas appeler `store`, d'où des littéraux dans `model` et un recalcul dans `tests/blocks.rs`.

Fonctions (pures, sans allocation) :
- `Block::span(self) -> BlockSpan` ;
- `Block::is_protected(self) -> bool` : vrai pour VALIDATION et HOLDOUT (lu par S12) ;
- `zone_of(ts) -> Zone` avec `Zone::{BeforeDev, Block(Block), Embargo(u8)}` ;
- `decision_window(block, window_end_ms) -> Result<(Ts, Ts), ModelError>` : `(span.start, min(span.end, window_end))`, erreur si la fenêtre se termine avant le début du bloc ou, pour un bloc fermé, après sa fin ;
- `is_purged(entry_signal_ms, exit_ms, decision_end_ms, end_of_window: bool) -> bool` (§3.4).

**Une seule écriture.** Les six instants ci-dessus n'apparaissent qu'une fois dans le code non-test de `tv4/src`. `tests/architecture.rs` reçoit un test `les_frontieres_de_blocs_ne_sont_ecrites_qu_une_fois` qui lit chaque fichier de `tv4/src` hors `model/blocks.rs`, coupé à sa première ligne `#[cfg(test)]` (convention du dépôt : le module de tests est en fin de fichier), commentaires retirés par `strip_line_comments`, et refuse les littéraux `1514764800000`, `1672531200000`, `1677628800000`, `1735689600000`, `1740787200000`, `1782864000000`, avec ou sans `_`. Les chaînes de dates (`"2023-01-01"`…) ne sont pas refusées : ce sont aussi des dates calendaires ordinaires (fin de `btcusd_2y`, par exemple), et le test ferait de faux positifs. État sur f2008e2 : `1_735_689_600_000` figure déjà dans `tv4/src/store/layout.rs` l.411, fin de l'année 2024 dans un test `#[cfg(test)]` de `Period::Year` (module ouvert l.368) ; c'est une frontière calendaire sans lien avec les blocs, exclue par la coupure au `#[cfg(test)]`. Aucune autre occurrence dans `tv4/src` ni `tv4/tests` (`grep -rnE` sur les six valeurs, avec et sans `_`).

### 3.2 Embargo de 59 jours

Les deux embargos font 59 jours (31 + 28), pas 60 : 04 §2.3 donne « 60 j » et des dates qui en donnent 59. S11 suit les **dates**, qui sont la frontière consignée (« dates fixes, une seule frontière pour tout le projet »). Sans effet sur le risque de fuite : chaque bloc est un dataset coupé à sa frontière, et la purge retire tout trade ouvert à la fin (§3.4). Écart n° 1 de §17, point n° 16 de §16.

### 3.3 Chauffe

Un dataset de bloc commence `WARMUP_PREFIX_DAYS_DEFAULT` = 210 jours avant le début du bloc : 2017-06-05 pour DEV, 2022-08-03 pour VALIDATION, 2024-08-03 pour HOLDOUT, 2025-12-03 pour FORWARD. 210 = 200 jours de la SMA200 1d (la plus longue chauffe admise, 04 §2.3 et §4.2) plus 10 jours de marge (une stratégie qui lit la valeur précédente d'une SMA200, un jour sans aucune minute en début de série). La valeur est une option de `tv4 dataset build` (`--warmup-days`, 0 à 400) parce que les tests en ont besoin courte ; la fenêtre de décision réelle est écrite dans le manifeste (`decision_window`), si bien qu'un dataset construit avec une autre chauffe est un autre dataset (autre fenêtre, donc autre `dataset_hash`) du même bloc.

Pendant le préfixe, les stratégies sont appelées dès la fin de leur warmup (convention de S5) et les indicateurs se calculent ; aucune entrée n'est acceptée (§8.3). Le préfixe lit le bloc précédent **et l'embargo** pour VALIDATION et HOLDOUT, le HOLDOUT pour FORWARD. La ligne « Embargo : Aucune lecture » de 04 §2.3 est lue comme « aucune décision, aucune métrique », pas comme « aucune donnée pour les indicateurs » : une SMA200 calculée au 2023-03-01 lit nécessairement janvier et février 2023. Une chauffe de FORWARD qui lit le HOLDOUT ne consomme pas de lecture de HOLDOUT au sens de G4. Point n° 6 de §16.

### 3.4 Purge

04 §2.3 : « tout trade ouvert à cheval sur une frontière est retiré des deux côtés ». Avec un dataset par bloc :
- **côté gauche** : aucune entrée n'est acceptée avant `decision_start` (§8.3), donc aucun trade ne commence dans le bloc précédent ou dans l'embargo. Le moteur le garantit, un `debug_assert!` et un test le vérifient ;
- **côté droit** : la fenêtre d'un dataset de bloc fermé s'arrête à la fin du bloc. Un trade encore ouvert à la fin est soldé par la clôture forcée existante (`ExitReason::ForcedClose`, `exit_type = end_of_window`) : son résultat est artificiel et dépendrait des données de l'autre côté. Il est **purgé**.

Définition codée une fois (`model::blocks::is_purged`) : un trade est purgé si son entrée a été décidée avant `decision_end` et s'il est soldé par la fin de fenêtre (`end_of_window`) ou sort à `exit_ms ≥ decision_end`. Dans un run de recherche, les deux conditions coïncident (la fenêtre s'arrête à `decision_end`), la seconde n'étant qu'une garde. FORWARD, ouvert à droite, a pour `decision_end` la fin de son dataset (`--to`) : un trade ouvert à la fin des données disponibles est purgé de la même façon, et un FORWARD reconstruit plus tard sur un dump plus long est un autre dataset (autre fenêtre).

Où : la classification est faite par `report` (§9.2) sur les trades rendus par le moteur ; le moteur ne retire rien de son journal ni de son equity. Les métriques de trades (effectif, expectancy, R, profit factor, distribution, verdict) portent sur les trades conservés ; les métriques d'equity (PnL net, drawdowns, rendement, exposition) portent sur l'equity de la fenêtre de décision (§8.2), PnL des trades purgés compris, et le bloc `research.purge` donne le PnL purgé pour que l'écart soit explicite. Point n° 5 de §16.

**Run qui couvre plusieurs blocs.** Il ne peut pas exister en mode recherche : `tv4 dataset build --block` refuse une fenêtre qui déborde la fin du bloc, et `tv4 backtest` vérifie `decision_window` à la lecture (§6.2). Un dataset **sans** `block` qui traverse des frontières (par exemple une fenêtre 2018-2026 construite à la main) reste un run s8, s9 ou s10 ordinaire, sans purge ni filtre : S11 n'y change rien, pour ne pas toucher aux goldens (§2). `tv4 backtest` écrit seulement sur stderr un avertissement quand la fenêtre d'un tel dataset recoupe VALIDATION ou HOLDOUT (stderr n'est ni haché ni comparé). La garde de S11 ne couvre donc que les datasets marqués (§9.5) ; le refus général est le travail de S12.

## 4. Univers trimestriel (points 1 et 6)

### 4.1 Paires candidates

- Entrées du zip de la forme `<PAIRE>_1.csv`, `PAIRE` validée par `KrakenPair::from_str` (`[A-Z0-9]{2,32}`, cotation reconnue par le plus long suffixe de `KNOWN_QUOTES`).
- Cotation canonique `USD` ou `USDT` seulement (liste `quotes` de `config/universe.toml`).
- Base hors de `excluded_bases` (`config/universe.toml`) : monnaies fiat (`EUR`, `GBP`, `CAD`, `JPY`, `CHF`, `AUD`, `USD`) et stablecoins (`USDT`, `USDC`, `DAI`, `TUSD`, `PYUSD`, `USDS`, `EURT`, `USDG`, `RLUSD` ; liste livrée, à compléter par le propriétaire). Sans cette liste, `USDTUSD` (base `USDT`) entrerait en tête de tout classement par volume sans être une paire de trading. Point n° 8 de §16.
- **Forme héritée.** Un nom qui correspond à `^[XZ][A-Z0-9]{3}[XZ](USD|USDT)$` (forme `XXBTZUSD` de l'API REST) n'est pas normalisé : il va dans `unrecognized_pairs` de `universe.json`, et le rapport de survivance liste toutes les entrées de cette forme. Le dump connu du dépôt nomme ses fichiers `XBTUSD_1.csv` (`fixtures/README.md`, section Provenance) : la forme héritée y est probablement absente, à vérifier sur la sortie du propriétaire.
- **Collision.** Deux entrées qui donnent le même symbole canonique (par exemple `XBTUSD` et un hypothétique `BTCUSD`) : erreur `UniverseError::SymbolCollision`, aucun fichier écrit.
- **Série bloquante.** Une paire dont `check_m1` rend un rapport bloquant (doublon divergent, OHLC incohérent, horodatage non aligné, valeur non finie) est écartée et listée dans `rejected_pairs` avec ses motifs. Elle ne pourrait de toute façon pas être ingérée (`cli/ingest.rs` l.461-465). Point n° 18 de §16.

### 4.2 Règle à la date `D`

`D` = premier instant d'un trimestre civil UTC (1er janvier, avril, juillet, octobre, 00:00). Pour chaque paire candidate et chaque `D`, à partir des 1m **réelles** contrôlées (aucune bougie synthétique) :

1. **Historique.** `first_active_ms ≤ D − 365 j` (365 × 86 400 000 ms), où `first_active_ms` est l'`open_time` de la première minute active (volume > 0) de toute la série. Les « 10 premiers jours après listing exclus » de 04 §2.2 sont impliqués : une paire de moins de 365 jours n'est jamais éligible.
2. **Continuité.** Sur `[D − 365 j, D)`, aucun trou ≥ `T` (`DEFAULT_QUOTE_GAP_MS` = 604 800 000 ms). Avec `a₁ < … < aₙ` les `open_time` des minutes actives de la fenêtre et `g(x) = x + 60 000` : trou initial `a₁ − (D − 365 j)`, trous intérieurs `aᵢ₊₁ − g(aᵢ)`, trou final `D − g(aₙ)` ; la paire est continue si tous sont `< T` (convention de S9 §4.3, où l'échéance est atteinte dès `t ≥ g0 + T`). Fenêtre sans minute active : non continue.
3. **Prix.** `last_close` = close de la dernière minute réelle d'`open_time < D` ; éligible si `last_close > 0,01`. Le prix d'une paire USDT est lu comme un prix USD (USDT ≈ 1 USD). Point n° 11 de §16.
4. **Volume quote 90 j.** `volume_90d(D) = Σ_{j = D−90 … D−1} Σ_{1m du jour j} close × volume`, accumulé jour par jour dans l'ordre chronologique puis sommé de zéro sur les 90 jours dans l'ordre des jours, exactement comme `RankTable::build` (`engine/priority.rs` l.62-84). Un jour sans minute vaut 0.
5. **USD contre USDT.** Pour une base donnée, la paire USD si elle est éligible ; sinon la paire USDT si elle l'est ; jamais les deux. Le volume n'est pas cumulé entre les deux paires. Point n° 7 de §16.
6. **Classement.** Les éligibles sont triés par `volume_90d` décroissant (`f64::total_cmp`), puis `first_active_ms` croissant (la plus ancienne d'abord), puis nom de paire Kraken en ordre d'octets. Le dernier critère ne départage qu'une égalité exacte de volume et d'ancienneté à la minute, que la règle 2 rend pratiquement impossible (deux volumes nuls sont exclus par la continuité) ; il existe pour que le résultat soit total et déterministe. Le rang de priorité des signaux de S9 (jamais l'alphabet) n'est pas concerné. Point n° 10 de §16.
7. **Top 12.** Les 12 premiers (`TOP_N = 12`) sont les membres du trimestre. Avec moins de 12 éligibles, tous le sont (la rampe de 5 à 13 de 04 §2.2).

Causalité : les règles 1 à 6 ne lisent que des minutes d'`open_time < D`. Test : modifier toute minute d'`open_time ≥ D` ne change ni les membres ni leur rang (seule la colonne `excluded_tfs` peut changer, §4.3).

Constantes : `TOP_N = 12`, `HISTORY_DAYS = 365`, `MIN_PRICE = 0.01` dans `research/universe.rs` ; `LIQUIDITY_WINDOW_DAYS` et `DEFAULT_QUOTE_GAP_MS` importées de `engine` (une seule définition). Elles sont recopiées dans le bloc `rules` de `universe.json`, donc dans `rules_hash` (§4.4). Les listes (`quotes`, `excluded_bases`, motifs de survivance, alias OKX) sont dans `config/universe.toml` (schéma `tv4-universe-config-v1`, `deny_unknown_fields`), dont le BLAKE3 des octets est écrit dans `universe.json` (`config_file_hash`).

### 4.3 Exclusion qualité par TF de décision (décision 8)

- Pour chaque membre, `store::quality_report(minutes_réelles, &Timeframe::ALL)` (même appel que l'ingestion, `cli/ingest.rs` l.495), puis, pour le trimestre `[D, D_suivant)`, la liste des TF de 5m à 1d dont la ligne a `excluded = true` (seuil strict > 1 %, `store/quality.rs` l.153). Le 1m n'y figure jamais, quel que soit son drapeau (04 §2.5 et §10 décision 8).
- La paire **reste membre** du trimestre ; le CSV le dit dans `excluded_tfs`. Le moteur, qui connaît le TF de décision de la stratégie, refuse les entrées de cette paire pendant ce trimestre si ce TF est listé (§8.3). Une paire exclue en 4h et gardée en 1d s'écrit `excluded_tfs = 1h;4h` (si le 1h est aussi au-delà du seuil) : une stratégie 1d y entre, une stratégie 4h non.
- **Univers fixe compris.** La décision 8 vaut pour toute (paire, TF de décision) (04 l.354), pas seulement pour les membres d'un univers trimestriel : ETH-USD 2018-Q1, exclu en 1d et en 4h, ne doit pas être tradé sur DEV par un run `--symbols BTC-USD,ETH-USD`. La source que lit le moteur est donc le **manifeste du dataset de bloc** : `tv4 dataset build --block` calcule `store::quality_report` sur la série 1m complète de chaque symbole lue dans le store (minutes réelles seulement, le store n'en contient pas d'autres) et écrit les trimestres exclus qui recoupent la fenêtre de décision (`quality_exclusions`, §6.1). Le calcul porte sur la série complète, pas sur la fenêtre du dataset : « seaux attendus depuis la première bougie de la série » et « fin de la plage observée » (`store/quality.rs` l.28-40) donneraient sinon un autre résultat pour un trimestre dont la dernière minute réelle tombe avant la fin. Avec `--universe`, les `excluded_tfs` du CSV de chaque membre et trimestre doivent égaler ce calcul, sinon `UniverseQualityMismatch` (code 1) : les deux viennent de la même série (zip contrôlé par `check_m1` et store ingéré depuis ce zip), un écart signale un bug.
- Pas de remplacement par la 13e paire : « un trimestre exclu sort la paire de l'univers de ce trimestre pour ce TF » (04 l.354) retire, il ne complète pas. Point n° 9 de §16.
- Limite assumée : la qualité d'un trimestre se juge sur les minutes de ce trimestre, donc après `D`. C'est une règle d'hygiène des données voulue par la décision 8 (le trimestre est jugé peu fiable), pas une décision de trading ; elle est signalée dans `universe.json` (`quality_uses_quarter_data: true`) et en §17.
- Cas réel à retrouver sur le Mac : BTC-USD 2018-Q1 exclu en 4h et gardé en 1d, ETH-USD 2018-Q1 exclu en 4h et en 1d (04 l.354, mesures du 15/10 sur les rapports d'ingestion). Ce sont des valeurs déjà mesurées par le propriétaire, que `tv4 universe build` et `tv4 dataset build --block DEV` doivent retrouver ; un écart signale un bug.

Un fichier par trimestre `D` tel que `D_suivant ≤ coverage_end` (trimestre entièrement couvert : la colonne qualité est alors complète). Avec la couverture annoncée par le manifeste du zip (2013-09-11 → 2026-09-30, `fixtures/README.md`), les trimestres de 2018-Q1 à 2026-Q3 sont produits (à confirmer par `_summary.json` du propriétaire). Plage par défaut : de 2018-Q1 au dernier trimestre couvert ; `--from-quarter` et `--to-quarter` la restreignent.

**`universe.json`** (schéma `tv4-universe-v1`, JSON canonique indenté à clés triées, `\n` final, comme les manifestes de S4) :

  "quarters": [ { "quarter": "2018-Q1", "date_ms": 1514764800000, "end_ms": …,
                  "file": "universe_2018-Q1.csv", "file_hash": "blake3:<hex des octets>",

- `quality_hashes` : hash `dsh-v1` du segment du membre sur `[D, D_suivant)`, lu par la qualité.
- `union` : toutes les paires membres d'au moins un trimestre, ordonnées par (premier trimestre de présence, rang dans ce trimestre). C'est l'ordre des jambes d'un run de recherche (§8.2) et la liste à ingérer (§15.3).
- **Identité, séparée du rapport.** `rules_hash` = `"blake3:" + hash::hash_json(rules)` (`model/hash.rs` l.55). L'identité d'univers d'un dataset ou d'un run est `window_hash(a, b)` = `"blake3:" + hash_json({ "rules_hash", "quarters": [{ "quarter", "file_hash" }…] })`, sur les seuls trimestres qui recoupent `[a, b)` (en pratique la fenêtre de décision), dans l'ordre chronologique. Elle n'est pas stockée dans `universe.json` : `store::universe` la calcule pour une fenêtre donnée. Un nouveau dump qui ajoute des trimestres, un autre jeu de `--at`, une autre `source` ou d'autres diagnostics ne changent donc ni l'identité d'un dataset DEV ni celle de ses runs ; changer un trimestre lu, ou les règles, la change.
- `report_hash` = `"blake3:" + hash_json` de l'objet entier sans `report_hash` : intégrité du fichier, contrôlée à la lecture, jamais recopiée dans un manifeste ni dans un run. Aucun horodatage de construction : deux constructions sur le même zip et la même configuration donnent des octets identiques.
- `--at <RFC3339>` (répétable) écrit `eligible_<AAAA-MM-JJ>.csv` : **tous** les éligibles à cette date (même colonnes, sans troncature à 12 ni `excluded_tfs`), et imprime leur nombre. C'est la commande du test 5 / 8 / 9 de 04 §2.2, dont la troisième date, 2018-12-31, n'est pas un début de trimestre.

**Lien avec le `dataset_hash`.** Un `input_hash` est le `dataset_hash` qu'aurait un dataset mono-série `skip` de ce membre sur `[D − 365 j, D)` (`docs/dataset-hash.md` §5.2) : il couvre les données lues par les règles 2 à 5 et se recalcule depuis le store. Il ne couvre **pas** ce que lisent la règle 1 et le départage par ancienneté de la règle 6, `first_active_ms`, qui vient d'avant la fenêtre : cette valeur est publiée dans la colonne `first_active` et `tv4 universe verify` la contrôle en relisant dans le store la première minute active de la série du membre. Les datasets de recherche portent `rules_hash` et `window_hash` (§6.1).

### 4.5 Déroulé et immutabilité

`tv4 universe build` :
1. ouvre le zip (`open_verified`), lit le manifeste et la fin de couverture par `store::time::parse_coverage_end` (même règle que l'ingestion). **Sans couverture lisible, la commande échoue** (`UniverseError::CoverageUnknown`, code 1), sauf si `--coverage-end <RFC3339>` est donné : le repli de l'ingestion sur `now_ms` (`cli/ingest.rs` l.360) rendrait `coverage_end`, la plage de trimestres produits et donc les fichiers dépendants de l'heure d'exécution. Si le manifeste donne une couverture et `--coverage-end` aussi, la plus petite des deux est retenue et imprimée ;
2. **passe 1** : pour chaque candidate, `rows_1m` puis `check_m1(rows, coverage_end)`, puis `research::universe::PairStats::from_m1(&candles)` : volumes quote par jour UTC, dernier close par jour, liste des trous entre minutes actives (`(g0, prochaine)`), première minute active, rapport de qualité ; la série 1m est libérée avant la paire suivante (pic mémoire = la plus longue série, de l'ordre de 1 Go pour XBTUSD d'après `fixtures/README.md` §Commande) ;
3. `research::universe::select(&stats, &dates, &config)` : éligibilité, choix USD/USDT, rang, top 12 par trimestre, éligibles des dates `--at` ;
4. **passe 2** : relit les seules paires de l'union (`check_m1` à nouveau) pour calculer `input_hash`, `quality_hashes` et les règles d'instrument dérivées (§4.7) ;
5. écrit les CSV, `instruments_kraken.toml`, puis `universe.json` (écriture durable de `store`, `universe.json` en dernier).

**Immutabilité.** Si `--out` contient déjà `universe.json`, chaque trimestre déjà présent doit être reproduit à l'octet (CSV et entrée de `quarters`) ; un écart donne `UniverseError::FrozenQuarterChanged { quarter }` et rien n'est écrit. Un dump plus récent n'ajoute que des trimestres. Les règles et la configuration doivent être identiques (`rules` égal), sinon `RulesChanged`. `instruments_kraken.toml` n'est pas figé : il couvre l'union, qui grandit avec les trimestres ; seules les règles des jambes réellement jouées entrent dans l'identité d'un run (§8.6).

`tv4 universe verify --root <R> --universe <DOSSIER>` : vérifie `file_hash`, `rules_hash` et `report_hash`, puis recalcule depuis le store chaque `input_hash`, chaque `quality_hashes` et chaque `first_active` (lecture vérifiée des partitions `kraken/<symbol>/1m`, `store::read_series_window`, ajoutée au lot B). Code 0 tout égal, 1 sinon, avec la liste des écarts. Il exige que l'union ait été ingérée (§15.3).

### 4.6 Tests (CI, données synthétiques)

Les données sont **synthétiques**, annoncées comme telles, et ne prétendent à aucune valeur de marché. Une paire synthétique a une minute active toutes les 6 heures (assez pour la continuité, 1 600 lignes sur 400 jours), sauf indication.

`tests/universe_build.rs` (fonctions de `research::universe`, sans zip) :
- **historique** : 365 j exactement (première minute active à `D − 365 j`) → éligible ; une minute plus tard → non ;
- **continuité** : trou intérieur de `T − 60 s` → éligible ; de `T` → non ; trou initial et trou final traités pareil ; un trou ≥ `T` antérieur à `D − 365 j` n'empêche rien (04 : EOS, GNO, XLM, REP reviennent 365 jours après leur retour) ;
- **prix** : `last_close` 0,01 → non ; 0,0101 → oui ; le prix lu est celui de la dernière minute avant `D`, pas celle de `D` ;
- **volume** : `volume_90d` égal à `RankTable::build(..).score_at(D, k)` au bit sur les mêmes bougies (`tests` peut lire `engine` et `research`) ; jour sans minute = 0 ;
- **USD/USDT** : `EEEUSD` et `EEEUSDT` éligibles → USD seul ; `EEEUSD` inéligible et `EEEUSDT` éligible → USDT ; `FFFUSDT` seul → USDT ;
- **exclusions** : `USDTUSD` et `EURUSD` écartés par `excluded_bases` ;
- **top 12** : 14 éligibles → 12 membres, les deux plus faibles volumes sortent ; égalité exacte de volume → le plus ancien d'abord, puis l'ordre d'octets du nom ;
- **causalité** : modifier une minute d'`open_time ≥ D` ne change ni membres ni rangs ;
- **qualité** : une paire à une minute par heure, à laquelle on retire toutes les minutes de 6 seaux 4h distincts du trimestre (6 seaux sur 546 ≈ 1,1 %), garde au moins une minute chaque jour : `excluded_tfs` contient `4h`, pas `1d` (critère 7, version synthétique) ; le 1m n'apparaît jamais ;
- **déterminisme** : deux constructions → mêmes octets ; listes triées en ordre d'octets quel que soit l'ordre des entrées du zip ;
- **identité** : ajouter un trimestre, changer `--at` ou `source` ne change pas `window_hash` des trimestres existants ; changer une ligne d'un CSV le change ;
- **instruments dérivés** (§4.7) : prix à une décimale → tick 0,1 (même valeur que `[kraken.BTC-USD]` de `config/instruments.toml`, croisée sur la fixture) ; prix à quatre décimales → 0,0001 ; artefact flottant (`0.30000000000000004`) → sans effet sur la décimale retenue ; plafond à 10 décimales.

`tests/cli_universe.rs` (zip synthétique écrit avec la crate `zip`, comme `tests/ingest_kraken.rs`) : `XBTUSD` normalisé en `BTC-USD` ; entrée piège `AIXBTUSD_1.csv` sans effet sur XBT ; collision → code 1 sans fichier ; nom hérité `XXBTZUSD_1.csv` → `unrecognized_pairs` ; série bloquante → `rejected_pairs` ; immutabilité (`FrozenQuarterChanged` si un octet d'une entrée du zip change sous un trimestre figé) ; `--at` écrit `eligible_*.csv` ; zip sans `MANIFEST.json` ni `--coverage-end` → code 1 sans fichier, avec `--coverage-end` → 0 ; `universe verify` après `ingest kraken` des membres → 0, après altération d'un fichier du store → 1.

Le test 5 / 8 / 9 de l'issue ne se vérifie que sur le dump complet (§15.2).

### 4.7 Règles d'instrument des jambes de recherche (point n° 21)

Le moteur exige une règle d'instrument par jambe : sans `--instruments-okx`, `toml_instruments` charge `InstrumentRules::load(exchange, symbol, …)` pour chaque symbole (`cli/backtest/portfolio.rs` l.257-270), qui rend `ModelError::InstrumentNotFound` si la paire manque (`model/instrument.rs` l.155-162) ; `config/instruments.toml` n'a que `[kraken.BTC-USD]`. Avec `--instruments-okx`, chaque symbole Kraken est converti en instId OKX et une paire non cotée rend `InstrumentNotListed` (l.208-212), ce qui est le cas de toute paire délistée de l'union (GNO, REP…, 04 §2.2). Sans règle nouvelle, tout run `--universe` réel échoue au chargement.

Règle recommandée (`decimals_v1`), calculée par `tv4 universe build` en passe 2 sur la série contrôlée complète de chaque paire de l'union :
- `tick_size` = 10^−d, où `d` est le plus petit entier de 0 à 10 tel que chaque prix `p` (open, high, low, close) vérifie `|p·10^d − round(p·10^d)| ≤ 1e-6` ; c'est la méthode qui a fixé le tick 0,1 de BTC-USD sur la fixture (`config/instruments.toml`, commentaire de tête : « prix à une décimale au plus ») ; un prix qui exige plus de 10 décimales donne 10 ;
- `lot_size` = 1e-8, la précision des volumes vérifiée sur la fixture (même commentaire), pour toutes les paires ;
- `min_qty` = 0 et `min_notional` = 0, comme BTC-USD aujourd'hui (« minimums à 0 : à valider ») : ces runs mesurent un edge sur données Kraken, l'exécutabilité au minimum d'ordre est jugée par G0 et G1 sur la liste live, avec le fichier OKX ;
- écrit dans `instruments_kraken.toml`, au format de `config/instruments.toml` (`[kraken.<SYMBOLE>]`, clés triées), avec en tête la méthode et la mention « dérivé du dump, minimums non mesurés » ; son BLAKE3 est dans `universe.json` (`instruments.file_hash`) et vérifié à la lecture.

Usage :
- `tv4 backtest --universe <DOSSIER>` lit les règles des jambes dans `instruments_kraken.toml` du dossier, à la place de `--instruments-file` (les deux ensemble → code 2). La paire de régime n'a pas besoin de règle (elle n'est pas tradée). `--instruments-okx` avec `--universe` est refusé (code 2) en S11 : G0 et G1 restent `not_applicable`, comme dans le chemin TOML de S9 ;
- en univers fixe (`--symbols`), rien ne change : `--instruments-file` (défaut `config/instruments.toml`) ou `--instruments-okx`. Le propriétaire peut passer `--instruments-file <DOSSIER>/instruments_kraken.toml` pour un run Kraken sur BTC et ETH ;
- les deux lignes d'un run (§9.1) utilisent les **mêmes** règles pour leurs jambes communes : l'écart entre les lignes ne mesure que l'effet de l'univers.

Le tick dérivé est un tick « le plus fin observé » : un tick trop fin est sans danger pour la simulation (les prix ne sont qu'arrondis plus finement), un tick trop grossier le serait. Les valeurs réelles ne sont connues qu'après le run du propriétaire (à valider sur `instruments_kraken.toml` renvoyé, §15.2).

## 5. Test de survivance (point 2)

### 5.1 Détection

- Motifs (`config/universe.toml`, `survivorship.expected`) : `ICN`, `BSV`, `LUNA`, `UST`, `FTT`, `WAVES` (04 §2.2). Un motif `X*` correspond à toute entrée `<PAIRE>_<n>.csv` dont le nom de paire **commence** par `X`, toutes cotations et résolutions confondues. `UST*` ne correspond pas à `USDTUSD` (le préfixe est `USD`), mais correspond à `USTCUSD` si elle existe (UST rebaptisé), ce qui est voulu.
- Pour chaque motif : la liste des paires trouvées, leurs résolutions présentes et les dates de première et dernière bougie (§5.2) ; `present` vrai s'il y a au moins une paire. Le préfixe peut attraper un actif homonyme plus récent (`ICN*` une paire `ICNT…`, `LUNA*` une paire `LUNA2…`, existence à valider sur le dump) : quand les paires d'un motif ont plusieurs bases canoniques différentes, l'entrée porte `review_needed: true` et la liste de ces bases, et le résumé imprimé le signale. `present` n'est pas corrigé par le code : le pilote tranche sur la liste publiée, dates à l'appui.
- Les absentes sont listées (`absent: ["ICN*", "BSV*"]` attendu d'après 04, à vérifier).

### 5.2 Dater le début du programme de dumps

Le zip ne donne pas cette date (le manifeste donne la couverture des données, `coverage_start` 2013-09-11, pas la date de début du programme). Ce qui se mesure :
- pour chaque paire du zip, la date de sa dernière bougie, lue dans l'entrée de plus grande résolution présente parmi `1440, 720, 240, 60, 15, 5, 1` (lecture de la dernière ligne d'une petite entrée ; la présence des entrées `_1440.csv` est à confirmer, d'où le repli) ;
- `delisted` = paires sans bougie dans les 90 derniers jours de la couverture (probablement délistées ; une paire seulement inactive y tomberait aussi, d'où la liste complète publiée) ;
- `earliest_delisted_present` = la plus ancienne dernière bougie parmi `delisted`. Une paire délistée avant le début du programme est absente du zip ; une paire délistée après y figure. La date de début du programme est donc **au plus** `earliest_delisted_present`, et au moins la date de délisting de la plus récente absente connue (BSV, avril 2019, d'après 04 §2.2, donnée externe recopiée dans le rapport comme hypothèse).

## 6. Datasets de recherche (points 3 et 5)

### 6.1 Manifeste : quatre champs facultatifs

```rust
pub struct DatasetManifest {
    … // champs existants inchangés
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub block: Option<Block>,                    // "DEV" | "VALIDATION" | "HOLDOUT" | "FORWARD"
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub decision_window: Option<[String; 2]>,    // [début du bloc, min(fin du bloc, fin de fenêtre)), RFC 3339
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub universe: Option<UniverseRef>,           // { rules_hash, window_hash } de l'univers lu au build (§4.4)
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub quality_exclusions: Option<BTreeMap<String, Vec<QuarterExclusion>>>,
                                                 // par symbole : [{ quarter: "2018-Q1", tfs: ["1h", "4h"] }], trimestres
                                                 // qui recoupent la fenêtre de décision et ont au moins un TF exclu (§4.3)
}
```

`quality_exclusions` est présent (éventuellement `{}`) sur tout manifeste qui porte `block`, absent sinon.

- **Hors de `dsh-v1`.** Le flux haché (`docs/dataset-hash.md` §2) ne change pas. Le `dataset_hash` reste un hash de contenu (exchange, symbole, TF, fenêtre, politique de trous, lignes) ; la fenêtre, qui y est déjà, sépare de toute façon les quatre blocs. Inclure `block` imposerait `dsh-v2` (nouveau préfixe, `docs/dataset-hash.md` §6), casserait le golden de S4 et obligerait à recalculer tous les manifestes du Mac. Point n° 2 de §16, bloquant.
- **Identité.** Un dataset de recherche est (`dataset_hash`, `block`). Deux manifestes au même contenu dont un seul porte `block` (un dataset construit à la main sur la même fenêtre) ont le même `dataset_hash`. La collision est levée sans toucher au `config_hash` : un run sur le dataset marqué est un run s11, dont `run_id_s11` contient `block`, la fenêtre de décision, l'identité d'univers et le hash des exclusions qualité (§8.6) ; un run sur le dataset non marqué est un run s9 ou s10 ordinaire (`run_id_s9`, `report/manifest.rs` l.156-166). Le `config_hash`, lui, reste celui de la configuration gelée, identique d'un bloc à l'autre (04 l.176 et l.186, G4).
- **Compatibilité.** Un manifeste existant n'a pas ces clés, se relit (`#[serde(default)]`), et son rendu reste identique à l'octet (`skip_serializing_if`). Le test de `store/manifest.rs` l.253 garde son JSON.

### 6.2 Construction et lecture

`store::build_dataset_research(root, &MultiBuildRequest, &ResearchMeta, now_ms)` avec `ResearchMeta { block, universe: Option<UniverseRef>, universe_quality: Option<…> }` :
- `gaps_policy` doit valoir `zero_volume_marked`, sinon `StoreError::ResearchGapsPolicy` ;
- la fenêtre doit commencer au plus tard au début du bloc et finir à la fin du bloc (DEV, VALIDATION, HOLDOUT) ou après le début du bloc (FORWARD), sinon `StoreError::ResearchWindow { block }` ; `decision_window` est calculé par `model::blocks::decision_window` ;
- **exclusions qualité** : pour chaque symbole, `quality_report` sur la série 1m complète du store (`read_series_window` sans borne) pour les TF de 5m à 1d, trimestres qui recoupent la fenêtre de décision (§4.3) ; avec un univers, comparaison aux `excluded_tfs` des CSV (`StoreError::UniverseQualityMismatch`) ;
- tous les contrôles et l'écriture de `build_partitions` (factorisée avec un paramètre `Option<&ResearchMeta>`, les deux constructeurs existants passant `None`) ;
- **immutabilité étendue** : un manifeste existant au même `dataset_hash` mais d'autre `block`, `decision_window`, `universe` ou `quality_exclusions` → `StoreError::DatasetMetaMismatch`, rien n'est écrit (aujourd'hui seul le hash est comparé, `store/dataset.rs` l.381-388). Cas attendu : un FORWARD reconstruit avec le même `--to` après une ingestion qui prolonge la série peut voir changer la qualité de son dernier trimestre (la « fin de la plage observée » recule) ; il est refusé et se construit sous un autre nom.

Lecture : `load_dataset_multi` est inchangé et rend le manifeste ; `store::research_meta(&DatasetManifest) -> Result<Option<ResearchInfo>, StoreError>` recalcule `decision_window` à partir de `block` et de `window` et refuse un manifeste où ils divergent, ou dont `block` est présent sans `decision_window` (ou l'inverse). `load_dataset` (mono-série) n'accepte pas un manifeste de recherche : `StoreError::ResearchNeedsPortfolio`.

### 6.3 CLI `tv4 dataset build` (§11)

`--symbol`, `--from` et `--to` deviennent facultatifs dans clap (aujourd'hui `required = true` sur `--symbol`, `cli/dataset.rs` l.27, et `from`, `to` de type `UtcMs` non optionnels, l.33-37) ; sans `--block`, une validation croisée les exige comme avant (code 2), si bien que le comportement sans bloc ne change pas.

Avec `--block <BLOC>` :
- `--from` est interdit (calculé : début du bloc − `--warmup-days`, défaut 210, 0 à 400) ; `--to` est interdit sauf pour FORWARD, où il est obligatoire (fin des données voulue, par exemple `2026-10-01T00:00:00Z`) ;
- `--gaps-policy` vaut `zero_volume_marked` par défaut ; toute autre valeur est refusée (code 2) ;
- `--tf` doit valoir `1m` (les TF supérieurs sont dérivés par `Mtf`, 04 §2.1) ;
- `--universe <DOSSIER>` (facultatif) : vérifie `universe.json` (hashes), prend comme symboles l'**union dédoublonnée** des membres des trimestres qui recoupent `decision_window` et des `--symbol` donnés (paire de régime hors univers, par exemple ; `--symbol BTC-USD` déjà membre n'est pas un doublon, alors que le build multi-séries refuse un doublon, `StoreError::DuplicateSymbol`, `store/dataset.rs` l.304-308), et écrit `universe` (`rules_hash`, `window_hash` de la fenêtre de décision) ;
- sans `--universe`, `--symbol` est obligatoire (univers fixe, comme F0 sur BTC et ETH).

Sans `--block`, rien ne change (défaut `skip`, `cli/dataset.rs` l.39-41).

Les quatre datasets du propriétaire (§15.4) : `research_dev`, `research_validation`, `research_holdout`, `research_forward_2026q3`. Leurs manifestes, sans secret, sont recopiés par le pilote sous `research/datasets/` et leurs `dataset_hash` inscrits en 03 §5.2 et 04 §2.3 (renvoi factuel).

### 6.4 Aucun fill dans une bougie synthétique (point 5)

Preuve par le code :
- `fill_gaps` crée les bougies absentes avec `open = high = low = close =` close précédent, `volume = 0.0`, `trades = None`, `synthetic = true` (`store/dataset.rs` l.770-783) ;
- `SimRules::zero_volume_no_fill` vaut vrai par défaut (`sim/rules.rs` l.67) et entre dans le `config_hash` (`sim_rules`) ;
- `Simulator::on_bar` n'exécute ni market, ni limit, ni stop, ni take-profit sur une 1m à volume nul (`sim/mod.rs` l.1054-1059) ; le moteur portefeuille passe chaque 1m par `Book::on_bar`, qui délègue à la jambe ;
- un dataset de recherche impose `zero_volume_marked` (§6.2), et le mode recherche refuse `zero_volume_no_fill = false` (`EngineError::ResearchNeedsZeroVolumeRule`).

Lien avec `s6.1` (« une minute absente vaut pas de fill », décision 9 et 04 §2.5) : l'activation d'un ordre est une heure d'horloge (`active_from_ms`), si bien qu'en `skip` comme en `zero_volume_marked` le premier fill possible est la première 1m **réelle** à partir de l'activation.

Tests (`tests/research_fills.rs`, lot F) :
- stratégie scriptée (`tests/common/scripte.rs`) qui soumet un achat market juste avant un trou, une limit au repos dont le niveau est traversé par la première 1m réelle après le trou, et un stop déjà franchi au moment où il devient actif pendant le trou : aucun `entry_fill_ms` ni `exit_ms` ne tombe sur une minute synthétique (masque `Columns::synthetic`, `store/columns.rs` l.176) ;
- même stratégie scriptée sur deux datasets identiques sauf `skip` contre `zero_volume_marked` : mêmes fills, mêmes prix, au bit (la stratégie ne lit pas de TF agrégé, dont les OHLC diffèrent légitimement entre les deux politiques) ;
- propriété (`proptest`, 256 cas) : séries à trous tirées au hasard, ordres scriptés tirés au hasard → aucun fill sur une minute synthétique.

## 7. Liste figée des paires OKX tradables en USDC (point 7)

### 7.1 Règle

À partir d'un fichier `tv4-instruments-v1` (S9 §8.5), une base est **tradable** si un instrument vérifie : `state == "live"`, et (`quote_ccy == "USDC"` ou `trade_quote_ccy_list` contient `"USDC"`). La seconde branche couvre la forme du carnet USD unifié d'OKX (l'ordre passe `tradeQuoteCcy = USDC`, 04 l.354) au cas où le compte listerait `BTC-USD` avec USDC dans `tradeQuoteCcyList` plutôt que `BTC-USDC` ; la forme réelle est à valider sur le fichier du propriétaire (S9 §8.7). Un instrument `suspend` ou `preopen` n'est pas tradable.

**Correspondance Kraken → OKX** : égalité de la base canonique Kraken (après `XBT` → `BTC`, `XDG` → `DOGE`) et de `base_ccy` OKX. Une table `okx_base_aliases` de `config/universe.toml`, **vide par défaut**, permet d'ajouter une correspondance explicite (jeton renommé) sur décision du propriétaire ; aucun alias n'est deviné. Point n° 14 de §16.

## 8. Moteur en mode recherche

### 8.1 Entrées

Nouveaux points d'entrée, les anciens étant inchangés :

```rust
pub struct ResearchSpec<'a> {
    pub block: Block,
    pub decision_start_ms: Ts,
    pub decision_end_ms: Ts,
    /// None : univers fixe (les jambes de la config) ; Some : univers trimestriel.
    pub universe: Option<&'a UniverseSchedule>,
    /// Exclusions qualité du manifeste (§6.1), pour toutes les jambes, univers fixe compris.
    pub quality: &'a QualitySchedule,
    /// Identité de recherche (§8.6), calculée par l'appelant : bloc, fenêtre, univers, ligne,
    /// sous-ensemble, valeurs par jambe. Le moteur la recopie dans son résultat sans la lire.
    pub identity: &'a ResearchIdentity,
}
pub fn run_portfolio_research(inputs: PortfolioInputs<'_>, research: &ResearchSpec<'_>) -> Result<PortfolioResult, EngineError>;
pub fn run_portfolio_profiles_research(inputs: ProfilesInputs<'_>, research: &ResearchSpec<'_>, observer: &mut dyn LoopObserver) -> Result<ProfilesResult, EngineError>;
```

`PortfolioConfig` et `PortfolioInputs` ne changent pas : ils sont construits par des littéraux dans 14 fichiers (dont 11 de tests), qu'un champ nouveau obligerait à toucher. Les fonctions existantes appellent le cœur commun avec `None`.

`UniverseSchedule` (`model/universe.rs`, nouveau) : trimestres triés `{ start_ms, end_ms, members: Vec<Member { symbol, rank: u8 }> }`, construit par `store::universe::load` depuis le dossier (hashes vérifiés). `QualitySchedule` (`model/universe.rs`) : par symbole, trimestres `[start, end)` et masque des TF exclus (`u8`, `Timeframe::bit()`), construit depuis `quality_exclusions` du manifeste. Le moteur en tire, avant la boucle, une table par jambe : intervalles `[start, end)` d'éligibilité pour le TF de décision des stratégies (`decision_tf`, identique pour toutes les jambes, la config n'en décrivant qu'une), intersection de l'appartenance à l'univers (si trimestriel) et de l'absence d'exclusion qualité. Un trimestre recoupant `[decision_start, decision_end)` absent du dossier → `EngineError::UniverseQuarterMissing { quarter }`.

**Cohérence de l'univers donné.** La CLI recalcule `window_hash` du dossier `--universe` sur la fenêtre de décision du dataset et le compare à `universe.window_hash` du manifeste : différent, ou manifeste sans univers → code 2 (`UniverseMismatch`). Un `--universe` ne peut donc pas être un autre univers que celui qui a choisi les symboles du dataset.

Le mode recherche n'existe qu'en portefeuille : l'activation par jambe, l'univers trimestriel, les deux lignes et le schéma s11 sont construits sur la grille multi-jambes et sur `MetricsS9` ; les doubler sur le chemin S8 (`run_cell`) ajouterait un second chemin à garder identique. Un run mono-paire de recherche est un portefeuille à une jambe (`--symbols BTC-USD`). `tv4 backtest` refuse un dataset de recherche sans `--symbols` ni `--universe` (code 2). Point n° 19 de §16.

**Régime.** Le moteur **n'impose pas** le filtre de régime : 04 §4.2 l'exige de toute hypothèse, mais c'est une condition de la fiche (G0), que S12 contrôlera avec la fiche gelée, pas une propriété du moteur ; aucune stratégie livrée ne lit encore le régime (`uses_regime()` vaut `false` par défaut, `strategy/mod.rs` l.310-312, et aucune stratégie ne le surcharge). Le bloc `research` publie `regime_used` (vrai si une stratégie a `uses_regime()`) ; la fumée de CI et le run de démonstration avec `sma_cross` (§15.5) sont donc acceptés, avec `regime_used = false`.

### 8.2 Activation par jambe

En S9, toutes les jambes démarrent à la même minute, la plus tardive de leurs fins de warmup et de la SMA200 du régime (`engine/portfolio.rs` l.804-824 ; S9 §6.3 et point 10 de §20). Avec un panel irrégulier (SOL listé en juin 2021 dans un DEV qui commence en 2018, 04 §2.2), ce départ commun repousserait tout DEV à 2022. En mode recherche :
- la jambe `k` est **vivante** à partir de `live_k = max(fin du warmup de k, prêt du régime)` ; avant, ni `on_bar`, ni stratégie (ses minutes restent dans la grille si d'autres jambes vivent) ;
- la grille commence à `min_k live_k` ; le contrôle `check_start` (indicateurs finis) se fait par jambe à `live_k` ;
- **enregistrement à partir de `decision_start`** : les minutes de grille d'`open_time < decision_start` sont jouées (stratégies, indicateurs, échéances de trou de cotation) mais ne sont **pas** poussées dans la grille enregistrée ni dans l'equity. `grid_minutes`, `grid_open_ms`, `equity`, `window_first_open_ms` et `bars_in_position` commencent à la première minute de grille d'`open_time ≥ decision_start`. Sans cela, l'exposition (`bars_in_position / grid_minutes`, `report/metrics_s9.rs` l.778-783), les jours bull et bear du régime (comptés depuis `window_first_open_ms`, `engine/portfolio.rs` l.1116-1127) et la durée d'annualisation compteraient jusqu'à 210 jours où toute entrée est interdite, et l'exposition, qui sert au benchmark « à exposition égale » et à F0, serait sous-estimée. L'equity du préfixe vaut le capital initial (aucune entrée possible), si bien que PnL et drawdowns ne changent pas ; `equity.csv` d'un run s11 commence à `decision_start` ;
- **jambes** : en univers trimestriel, les membres des trimestres qui recoupent `[decision_start, decision_end)`, dans l'ordre de `union` (§4.4), filtrés par la CLI pour la ligne `okx_usdc` (§9.1), plus la paire de régime lue hors univers (S9 écart 3). Ce sont exactement les symboles d'univers du dataset (§6.3) : une paire délistée avant le bloc ou listée après n'y est pas, et `SymbolNotInDataset` (`engine/portfolio.rs` l.715-720) ne peut pas se produire. En univers fixe, les jambes de `--symbols`.

Hors mode recherche, le départ commun de S9 est inchangé (point n° 12 de §16).

### 8.3 Filtre des entrées

À l'étape 5 (soumission) de S9 §4.2, pour un signal de classe `Entry` (`EnterLong`, `PlaceLimit` d'achat, `engine/signals.rs` l.25-30) sur la jambe `k` à `now_ms` :
1. `now_ms < decision_start` ou `now_ms ≥ decision_end` → refus, compteur `entries_outside_decision_window` ;
2. univers trimestriel et `k` non membre du trimestre de `now_ms` → refus, `entries_not_in_universe` ;
3. `decision_tf` exclu pour `k` et le trimestre de `now_ms` dans `QualitySchedule` (univers fixe comme trimestriel) → refus, `entries_excluded_quality` (jamais pour un TF de décision 1m).

Le trimestre se lit à `now_ms` (clôture de la 1m), demi-ouvert : la décision prise à la clôture de la dernière bougie 1d d'un trimestre (`now_ms` = 00:00 du premier jour du trimestre suivant) relève du trimestre suivant, dont l'univers ne lit que des données antérieures. Les signaux de sortie, `MoveStop` et annulations ne sont jamais filtrés : « les positions en cours vont à leur terme » (04 §2.2). La lecture est O(1) amortie (curseur par jambe, le temps étant croissant).

**Sortie de l'univers en cours de route.** À la première minute de la grille d'`open_time ≥` début du trimestre où une jambe à plat devient inéligible (hors univers ou exclue par la qualité pour `decision_tf`), ses entrées en attente sont annulées par `Book::cancel_entries_quote_gap` (`sim/book.rs` l.346-348, mêmes ordres visés : `Enter` et limits d'achat d'une jambe à plat), comptées dans `orders_cancelled` et dans `research.entries_cancelled_universe`. L'annulation a lieu à l'**étape 1** de S9 §4.2, avant tout `Book::on_bar` de la minute, pour toutes les jambes dans l'ordre du rang, que la jambe ait ou non une bougie à cette minute, exactement comme `force_quote_gaps` (`engine/portfolio.rs` l.1206-1229), et après lui. Sinon une entrée décidée à `now_ms = D − 60 s` et active à `D` remplirait à la minute `D` avant d'être annulée. Test : entrée soumise à `now_ms = D − 60 s`, jambe hors univers au trimestre de `D` → aucun fill, une annulation comptée. `sim` n'est pas modifié.

Identité de l'entonnoir d'entrée d'une jambe en mode recherche : `entry_signals = entry_orders + entry_rejections.total() + max_positions_rejected + entries_outside_decision_window + entries_not_in_universe + entries_excluded_quality`. Les trois compteurs sont dans un struct nouveau `ResearchLegCounters`, rendu par `PortfolioResult::research: Option<ResearchResult>` (champ facultatif ; `PortfolioResult` n'est construit que dans `engine/portfolio.rs` l.1131) : `SignalRejections` (17 champs épinglés par S8) et `LegResult` ne changent pas.

### 8.4 Fin de fenêtre

Inchangée : clôture forcée de toutes les positions à la dernière bougie (`end_of_window`). Ces trades sont purgés par `report` (§3.4). Le moteur rend `decision_start_ms`, `decision_end_ms`, `live_k` par jambe et les compteurs dans `ResearchResult`.

### 8.5 Profils de coûts

`run_portfolio_profiles_research` applique la même activation et le même filtre aux trois profils, la préparation restant partagée (S10 §9). Les compteurs de recherche sont propres à chaque profil (les fills diffèrent).

### 8.6 `config_hash`

**Principe.** Le `config_hash` est l'identité d'une configuration gelée : c'est lui que nomment la fiche, le registre et le claim (04 l.176 « Claim holdout : … pour la config <config_hash>, inscrit AVANT lecture » ; l.186, registre par (…, `config_hash`, `dataset_hash`, bloc lu, …), le bloc étant une colonne distincte ; G4, « claim … avec le `config_hash` AVANT lecture »). Une même configuration doit donc garder le même `config_hash` sur DEV, VALIDATION et HOLDOUT, et sur ses deux lignes : sinon la configuration gelée sur DEV n'aurait pas le hash du claim, et les deux lignes d'un rapport HOLDOUT feraient deux lectures. Ce n'est pas le cas aujourd'hui en portefeuille : `PortfolioRunConfig` contient la liste des jambes (`portfolio.universe`, l.85), les règles d'instrument par symbole (`instruments`, l.131) et, en s10, les valeurs de coûts résolues par jambe (`costs.legs`, l.106), qui changent toutes d'un bloc à l'autre avec un univers trimestriel et d'une ligne à l'autre. S11 sépare donc deux objets hachés.

**1. `config_hash` d'un run de recherche.** Le même `PortfolioRunConfig`, schéma inchangé (`tv4-portfolio-config-v1` ou `-v2`), avec un champ facultatif absent hors recherche (le JSON v1 et v2 reste identique à l'octet, `REFERENCE_JSON` de `engine/portfolio_config.rs` le prouve), et, en recherche seulement, les trois tables par jambe **vidées** : `portfolio.universe = []`, `instruments = {}`, `costs.legs = {}` (s10). Ce qu'elles décrivaient passe dans l'identité de recherche (point 2).

```rust
#[serde(skip_serializing_if = "Option::is_none")]
pub research: Option<ResearchHashed>,

pub struct ResearchHashed {
    pub blocks_version: &'static str,     // "b1"
    pub universe_spec: UniverseSpec,      // Fixed { symbols: Vec<String> /* --symbols, triés, avant filtrage de ligne */ }
                                          // | Quarterly { rules_hash: String }
    pub decision_tf: Timeframe,           // TF d'exclusion qualité lu
    pub purge_rule: &'static str,         // "end_of_window_v1"
}
```

Aucun champ ne dépend du bloc, de la fenêtre, des trimestres lus, de la ligne ni du sous-ensemble. Le capital reste hors du hash (décision du 28/10).

**2. Identité de recherche.** Ce qui distingue deux runs de même `config_hash` sur le même `dataset_hash` :

```rust
pub struct ResearchIdentity {
    pub block: Block,
    pub decision_start_ms: Ts,
    pub decision_end_ms: Ts,
    pub universe_window_hash: Option<String>,  // window_hash du manifeste, null en univers fixe
    pub quality_hash: String,                  // hash_json de quality_exclusions du manifeste
    pub line: Line,                            // "full" | "okx_usdc"
    pub subset_hash: Option<String>,           // null pour full
    pub legs_hash: String,                     // hash_json { universe: [ordre joué], instruments: {…},
                                               //   instruments_hash, costs_legs: {…} }
}
research_identity_hash = "blake3:" + hash_json(ResearchIdentity)
run_id_s11 = blake3_hex("{config_hash}|{dataset_hash}|{start_ms},{end_ms}|{initial_cash:?}|{research_identity_hash}")
```

`run_id_s11` prolonge `run_id_s9` (`report/manifest.rs` l.156-166) du seul `research_identity_hash`. Un résultat de recherche n'est reproductible qu'avec (`config_hash`, `dataset_hash`, `research_identity_hash`, capital, commit) : c'est une extension de la règle de travail de `CLAUDE.md` (« `config_hash`, `dataset_hash`, commit, et le capital en portefeuille »), sur le modèle de la décision du 28/10 qui a sorti le capital du hash. Elle est soumise au propriétaire (point n° 2). `research_identity` et son hash sont écrits dans `metrics.json` (§9.2) ; `tv4 verify` les compare.

## 9. Rapports s11, deux lignes, `tv4 verify` (point 8)

### 9.1 Deux runs, pas deux agrégations

La ligne « sous-ensemble tradable » doit dire ce que le paper jouerait (« seul le sous-ensemble va en paper », 04 §2.2). Une agrégation des trades du run complet restreinte aux paires tradables serait fausse : le cash partagé, `max_positions`, la priorité de rang et les échéances de trou de cotation (vérifiées aux minutes de la grille, S9 §4.2 étape 1) dépendent des jambes présentes. D'où **deux runs** sur le même dataset :
- `full` : toutes les jambes de l'union ;
- `okx_usdc` : les jambes dont la base est dans le fichier `tv4-pair-subset-v1` (§7) ; la paire de régime reste lue hors univers si elle en sort.

Avec `--costs`, chaque ligne est un dossier de profils de S10. Une ligne vide (aucune base tradable) est une erreur (`LinesSubsetEmpty`).

Les deux lignes ont le **même `config_hash`** (§8.6 : la ligne et le sous-ensemble sont dans l'identité de recherche) et deux `run_id_s11`. Leurs jambes communes ont les mêmes règles d'instrument (§4.7) et, avec `--costs`, les mêmes valeurs de coûts par jambe.

Écrit en dernier dans `DIR/` (comme `profiles.json` de S10), JSON canonique compact à clés triées :

### 9.4 Quand les deux lignes sont exigées

- VALIDATION et HOLDOUT : `--okx-subset` obligatoire (code 2 sinon). Le paper (jalon 3) réutilisera `tv4-lines-v1`.
- DEV et FORWARD : facultatif ; sans lui, un seul run s11 est écrit.

### 9.5 Garde provisoire avant S12

03 §15.1 ligne 11 confie à S12 le refus de VALIDATION et HOLDOUT sans fiche gelée ni claim. En attendant, S11 refuse tout run sur un dataset dont `block.is_protected()` (code 2, message « lecture protégée : garde-fous de S12 non livrés »), sauf avec l'option cachée `--unguarded-protected-read`, qui écrit `research.guard = "unguarded"` dans chaque rapport et sur stderr. Elle sert aux tests et à une vérification de bout en bout explicitement demandée ; S12 la remplace. Point n° 13 de §16.

**Portée, dite telle quelle.** La garde arrête une lecture **par la voie de recherche** (dataset de bloc). Elle n'empêche pas de lire la même période autrement : un dataset construit sans `--block` sur la fenêtre du HOLDOUT se joue comme un run s8, s9 ou s10, avec un simple avertissement sur stderr (§3.4), et retirer `block` d'un manifeste, qui n'est haché nulle part (`store/manifest.rs` l.5), suffit à la contourner. Un refus de toute fenêtre qui recoupe VALIDATION ou HOLDOUT, `block` ou pas, n'est pas retenu en S11 : les goldens `portfolio_2legs` et `portfolio_profiles` et `tests/cli_portfolio.rs` jouent par la CLI des données synthétiques datées de janvier 2024 (§2), et ce refus les casserait. C'est une garde d'honnêteté au sens de 04 §4.4 (« suffisante pour une personne honnête avec elle-même ») ; le contrôle sur la fenêtre de toute lecture et l'identité hachée du dataset de bloc relèvent de S12.

- **Dossier de profils s11** (run de recherche avec `--costs`) : accepté. - `--universe` ou `--okx-subset` sur un dataset sans `block` → code 2 ; dataset de recherche sans `--symbols` ni `--universe` → code 2 ; `--okx-subset` absent sur VALIDATION ou HOLDOUT → code 2 ; `--universe` dont le `window_hash` diffère de celui du manifeste → code 2 ; `--universe` avec `--instruments-file` ou `--instruments-okx` → code 2 (§4.7).
- `tv4 universe build` et `survivorship` sans couverture lisible ni `--coverage-end` → code 1 (§4.5).
- Sortie standard de `universe build` : trimestres produits, nombre de membres par trimestre, éligibles de chaque date `--at`, paires écartées et non reconnues, `rules_hash`, `report_hash`, nombre de règles d'instrument écrites.
- Codes : 0 succès, 1 erreur applicative, 2 usage (dont les refus ci-dessus), 3 `verify` différent.
- `--pairs-from-universe` évite de recopier à la main l'union (30 à 40 paires attendues sur 2018-2026, ordre de grandeur à vérifier sur la sortie du Mac).

D'où ≈ 113 octets par ligne et par paire présente sur tout le bloc : 4,0 Go pour 12 paires, 6,6 Go pour 20, 9,9 Go pour 30, 13,3 Go pour 40, avant les TF agrégés, les indicateurs et le carnet. Le nombre de paires de l'union sur DEV n'est pas connu ici (§11 : 30 à 40 sur 2018-2026, toutes périodes confondues), et les paires listées en cours de bloc ont moins de lignes. 03 §15.1 ligne 1 (l.872) donne ≈ 2,6 Go pour 12 paires × 8,5 ans en SoA à 6 colonnes et une machine de 15 Go, et 03 §5.1 (l.244) recommande de traiter par paire au-delà. Parades prévues, dans l'ordre : (1) le chargement du mode recherche consomme les `Columns` (conversion par valeur, colonne par colonne, libérée à mesure), ce qui retire une copie (≈ 57 octets par ligne, 5,0 Go à 30 paires) ; c'est une modification de `engine/portfolio.rs` limitée au point d'entrée de recherche, `run_portfolio` gardant son chemin ; (2) si l'union DEV dépasse ce que la machine tient, le propriétaire lance d'abord le run de démonstration sur un sous-ensemble fixe (`--symbols` des 7 paires les plus anciennes) et le pilote décide de la suite sur la mesure. Le run de §15.5 donne la mémoire réelle (`timings` et pic à relever par `/usr/bin/time -l`, à valider).
- `tv4 universe build` lit en flux toutes les entrées 1m USD et USDT du dump ; sa durée et sa mémoire sur le dump complet ne sont pas mesurables ici (à mesurer sur le Mac, §15.2) : le pic attendu est celui de la plus longue série, comme `ingest kraken`.

## 17. Écarts et limites connues

1. **Embargos de 59 jours** au lieu des « 60 j » de 04 §2.3 (§3.2, §16 n° 16).
2. **Couverture du dump.** 04 §2.1 (l.47) écrit « jusqu'au 2026-06-30 », alors que le manifeste du zip lu par le propriétaire annonce une couverture jusqu'au 2026-09-30 (`fixtures/README.md`). FORWARD 2026-Q3 se construit donc sur le même zip, sans attendre un dump trimestriel. À confirmer par `_summary.json` (champ `raw` du manifeste), puis corriger 04 §2.1 (fait, pas règle).
3. **Qualité non causale** : l'exclusion d'un trimestre se juge sur ses propres minutes (§4.3), comme le veut la décision 8.
4. **Estimation de la date de début du programme de dumps** : une borne haute mesurée et une borne basse tirée de 04 (BSV), pas une date (§5.2). Une paire inactive plus de 90 jours sans être délistée entre dans la liste `delisted` ; la liste est publiée pour revue.
5. **Trimestres postérieurs à 2026-Q3** : le calcul exige 365 jours d'historique de toutes les paires USD, donc un nouveau dump complet. Si Kraken ne publie que des dumps trimestriels incrémentaux, il faudra une source store (ingestion de toutes les paires candidates) : hors S11.
6. **Pas de sous-ensemble « paires les plus anciennes » pour DEV** (04 §2.2, « publier aussi les résultats DEV sur le sous-ensemble XBT, ETH, LTC, ETC, ZEC, XMR, XRP ») : le format `tv4-pair-subset-v1` le permet, la ligne n'est pas livrée par S11 (à S13 ou S18 avec le runner de campagne). Soumis au point n° 24.
7. **Paires « basis »** : 04 §2.5 veut les validation et holdout des paires marquées `basis` sur des données OKX. Les datasets de S11 sont Kraken ; un dataset de bloc OKX se construit avec la même commande (`--exchange okx`), mais sans univers trimestriel OKX ni règle de bascule automatique.
8. **Métriques d'equity non purgées** (§3.4, §9.2) : `pnl_net`, drawdowns et rendement incluent le PnL des trades purgés ; l'écart est publié. Elles portent sur la fenêtre de décision, pas sur la chauffe (§8.2).
9. **Liste OKX d'aujourd'hui appliquée au passé** : la ligne `okx_usdc` utilise la liste de 2026 sur VALIDATION et HOLDOUT ; c'est la définition de 04 §2.2, et elle surestime ce qui aurait été tradable sur OKX USDC avant le 21/08/2025 (cotation du carnet USDC, 04 §2.1).
10. **5 / 8 / 9** : valeurs de 04 reconstituées à partir d'un jeu dérivé ; des règles de S11 (stablecoins, USDT, trou ≥ 7 jours) peuvent faire bouger ces comptes. La spécification ne relâche pas pour autant « tout écart signale un bug de lecture » : la conduite à tenir est soumise au point n° 22.
11. **Paper** : la partie « paper » du critère 3 n'est pas livrée (jalon 3), point n° 25.
12. **Règles d'instrument dérivées** (§4.7) : tick « le plus fin observé », lot 1e-8 et minimums à 0 pour toutes les paires Kraken de recherche ; ce ne sont pas des règles lues chez Kraken. Elles servent l'arrondi des ordres simulés ; l'exécutabilité au minimum d'ordre reste jugée par G0 et G1 sur la liste live avec le fichier OKX.
13. **Garde provisoire partielle** (§9.5) : elle ne ferme que la voie des datasets marqués.
14. **Mémoire du run DEV** (§12.2) : estimation seulement, de 3,3 à 13,3 Go de données 1m selon le nombre de paires et la parade appliquée ; à mesurer sur le Mac.
