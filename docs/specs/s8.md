## 2. `metrics.json`, schéma `tv4-metrics-s8`

### 2.1 Règles générales

- JSON canonique (clés triées, `report::write_json_atomic`), un `\n` final, inchangé.
- Rien qui dépende de la machine, de l'heure, du chemin ou du commit. Conséquence : le bloc `engine` (qui porte `git_sha`) **quitte** `metrics.json` pour `manifest.json` (03 §7.3, écart S3 point 5, l'avait prévu). Sans cela, le golden de run changerait à chaque commit.
- Toute clé est toujours présente ; une valeur indéfinie vaut `null` (plus de `skip_serializing_if` dans les blocs S8). Les tableaux à clé (par année, par type de sortie) sont des tableaux d'objets triés par la clé.
- Sommes et moyennes : boucles `for` explicites dans l'ordre des trades du simulateur (jamais `.sum()` sur des flottants, 03 §7.4). Aucune fonction libm hors du bloc `approx` (§2.5). Un pic courant se met à jour par `if x > peak { peak = x }`, jamais par `f64::max` (03 §7.4, signe du zéro).
- Montants en monnaie de cotation des données (USD pour Kraken BTC-USD), durées et instants en millisecondes UTC, ratios en fraction (0,0123 = 1,23 %).

### 2.4 Objet Dd (drawdown)

Série `e_j` (equity à la clôture de la 1m `j`, `CellResult.equity`), instants `τ_j = open_time_j + 60 000`. `peak` part de `initial_cash` ; pour chaque `j` dans l'ordre : `if e_j > peak { peak = e_j; peak_at = Some(τ_j) }`, puis `dd_j = 1 − e_j / peak`. Le point retenu est le premier `j` qui maximise `dd_j` (mise à jour sur `>` strict).

| Clé | Type | Définition |
|---|---|---|
| `pct` | f64 | `max dd_j`, ≥ 0 (fraction) ; 0.0 si l'equity ne passe jamais sous son pic |
| `quote` | f64 | `peak − e_j` au point retenu, ≥ 0 |
| `peak_ms` | i64\|null | `peak_at` au point retenu ; `null` si le pic est le capital initial ou si `pct = 0` |
| `trough_ms` | i64\|null | `τ_j` du point retenu ; `null` si `pct = 0` |

La clôture forcée (qui suit la dernière 1m) n'entre pas dans la série : `equity_final` reste dans `metrics.json` à part. Écrit tel quel dans la doc des écarts S8.

### 2.5 Bloc `approx` (seul usage de la libm)

| Clé | Type | Définition |
|---|---|---|
| `ulp_tolerance` | u32 | `20` (constante `approx::ULP_TOLERANCE`) : écart maximal admis, en ULP, entre chaque valeur du bloc et la référence exacte (voir ci-dessous, tolérance ULP en CI) |
| `ln_return` | f64\|null | `(equity_final / initial_cash).ln()` ; `null` si le ratio ≤ 0 |
| `return_annualized` | f64\|null | `exp_m1(y × ln(ratio))` avec `ratio = equity_final / initial_cash` et `y = 31 557 600 000 / span_ms` (année de 365,25 jours, division IEEE), soit `ratio^y − 1` ; `null` si `span_ms < 30 × 86 400 000`, si le ratio ≤ 0 ou si le résultat n'est pas fini. Sur la fixture (fenêtre jouée d'environ 7,4 jours) il vaut donc `null`. La forme naïve `ratio.powf(y) − 1` est écartée : près de `ratio = 1`, la soustraction de 1 amplifie l'écart d'1 ULP que la libm laisse sur `powf` (956 ULP pour un ratio 1,001 sur 730 jours, plus de 4 millions pour un ratio 1,0000001 sur un an), alors que `exp_m1` reste bien conditionnée |

Calculé dans `tv4/src/report/approx.rs`, **seul fichier** du crate autorisé à appeler `ln`, `ln_1p`, `log`, `log2`, `log10`, `exp`, `exp2`, `exp_m1`, `powf`, `powi` et les trigonométriques. Un test d'architecture (lot A, dans `tests/architecture.rs`) parcourt `tv4/src/**` (hors `report/approx.rs`, commentaires retirés) et échoue sur `.ln(`, `.ln_1p(`, `.log(`, `.log2(`, `.log10(`, `.exp(`, `.exp2(`, `.exp_m1(`, `.powf(`, `.powi(`, `.sin(`, `.cos(`, `.tan(`, `.cbrt(`, `.hypot(`, `.atan(`, `.atan2(`. État actuel vérifié : aucune occurrence dans `tv4/src`, `tests` ni `benches`.

Tolérance ULP en CI (critère « comparés en CI à une tolérance ULP documentée », 03 §7.4) : test unitaire de `approx.rs` sur une table de 23 cas qui appellent `compute()` : le cas `ln_return` de la fixture (ratio 0,98494, 7,4 jours, annualisé `null`), les ratios 0,5, 0,9, 0,99, 0,9999999, 1,0000001, 1,001, 1,01, 1,1, 1,2, 1,5, 2 et 3 sur des durées de 30 jours à 10 ans, et trois cas extrêmes (ratios 3, 5 et 10 sur 30-31 jours). Les références sont calculées par Python `decimal` à 50 chiffres puis arrondies au `f64` le plus proche ; la commande exacte est recopiée en commentaire du test. Assertion : distance ULP (différence des `to_bits` pour deux finis de même signe) ≤ `ULP_TOLERANCE` sur `ln_return` **et** sur `return_annualized` de chaque cas, plus `ulp_tolerance == ULP_TOLERANCE`.

Origine de la borne de 20 : écart maximal mesuré sur la table, glibc 2.39, = 18 ULP, atteint par le cas extrême du ratio 10 sur 30 jours (`|x|` = `|y × ln(ratio)|` = 28 ; les cas extrêmes des ratios 3 et 5 sur 30-31 jours donnent 12 et 13 ULP), arrondi à 20. `ln_return` tient 0 ULP partout ; `return_annualized` tient 0 à 2 ULP tant que `|x| ≤ 3` (annualisé jusqu'à +1 900 %), le cas courant : l'erreur croît d'environ `|x|` ULP, les arrondis de `ln` et du produit étant propagés par `exp_m1`. Le test échoue aussi si la borne devient plus lâche de plus de 2 ULP que le pire cas mesuré, et un autre test montre que `powf − 1` perd plus de 1 000 ULP là où `exp_m1` en tient 1. La libm d'Apple n'est pas mesurée : à relire au premier `cargo test` sur le Mac (à valider).

Conséquence assumée : deux runs de deux architectures peuvent différer de quelques ULP dans `approx` (chacun reste à au plus `ULP_TOLERANCE` de la référence exacte, donc l'écart entre deux plates-formes va jusqu'à 2 × `ULP_TOLERANCE` pour un cas extrême), donc `tv4 verify` les déclarera différents ; sa sortie liste les chemins JSON en écart, ce qui montre que l'écart est confiné à `approx`. Le golden de run (§13) compare `metrics.json` sans `approx` à l'octet et chaque valeur de `approx` à `ULP_TOLERANCE` ULP du fichier versionné, avec la même constante importée du code (pas de copie). Aucun golden actuel n'expose l'écart de 2 × `ULP_TOLERANCE` (`return_annualized` y est `null`, fixtures de moins de 30 jours) ; un futur golden de 30 jours ou plus avec un ratio extrême serait à revoir. Garder `return_annualized` (utile pour le verdict à 12 mois contre le Livret A) ou laisser `approx` réduit au seul test de tolérance : à valider (§17 point 3).

### 2.6 Bloc `funnel` (entonnoir, 04 §9 point 4, 03 §15.1 ligne 4)

Classement des signaux par le moteur, au moment de la soumission : **entrée** = `EnterLong` ou `PlaceLimit { side: Buy }` ; **sortie** = `ExitLong` ou `PlaceLimit { side: Sell }` ; **autre** = `MoveStop`, `CancelPending`, `CancelSlot`.

| Clé | Type | Définition |
|---|---|---|
| `evaluations` | u64 | appels de `Strategy::on_bar` |
| `raw_entry_signals` | u64\|null | déclaré par la stratégie via `Strategy::funnel()` (§7.3) ; `null` si elle ne déclare rien |
| `entry_filtered_by_reason` | objet `{motif: u64}` | déclaré par la stratégie ; `{}` si rien. `sma_cross` : `stop_not_positive`, `trend_filter` |
| `entry_signals` | u64 | signaux d'entrée émis |
| `entry_rejected_by_reason` | objet `SignalRejections` | les 17 motifs, comptés sur les seuls signaux d'entrée |
| `entry_orders` | u64 | signaux d'entrée acceptés par `submit` |
| `entry_not_filled_by_reason` | objet | `insufficient_cash` (= `sim.buys_rejected_insufficient_cash`), `below_minimum` (= `sim.buys_rejected_below_minimum`), `volume_share` (= `sim.buys_rejected_volume_share`), `invalid_risk_at_fill` (= `sim.entries_invalid_risk_at_fill`), `dropped_while_long` (= `sim.entries_dropped_while_long`), `other` = `entry_orders − entry_fills − Σ des cinq` (ordres d'achat expirés, annulés ou encore en attente à la fin ; les compteurs `limits_expired`, `orders_cancelled`, `orders_unfilled_at_end` du simulateur ne distinguent pas achat et vente). | `entry_fills` | u64 | lots ouverts = nombre de `lot_id` distincts de `T` (toute position est soldée par la clôture forcée, donc tout lot apparaît) |
| `trades` | u64 | `= n_trades` |
| `exit_signals`, `exit_orders` | u64 | signaux de sortie émis, acceptés |
| `other_signals`, `other_accepted` | u64 | signaux « autres » émis, acceptés |
| `exits_by_type` | objet | nombre de trades par `exit_type` (§3.3), les sept valeurs écrites au jalon 1 toujours présentes, 0 compris |

Invariants testés : `entry_signals + exit_signals + other_signals = signals.emitted` ; `entry_orders + exit_orders + other_accepted = signals.accepted` ; `entry_rejected_by_reason + rejets des autres classes = signals.rejected_by_reason` champ à champ ; pour `sma_cross`, `raw_entry_signals − Σ entry_filtered_by_reason = entry_signals`.

Correspondance avec les « rejets cap / cash / notional » de 03 §15.1 ligne 3 : un rejet n'a pas de fill, donc pas de ligne de trade ; il est compté ici. Cash : `entry_rejected_by_reason.insufficient_quote` + `entry_not_filled_by_reason.insufficient_cash` ; notional ou minimum : `below_minimum` (aux deux étages) ; cap de volume : `entry_not_filled_by_reason.volume_share`. Le choix de compter les rejets dans l'entonnoir plutôt que de les écrire en lignes est à valider (§17 point 7), comme un éventuel journal ligne à ligne des rejets (`rejections.csv`) au jalon 1.5.

## 4. `equity.csv`

- Option `--equity-step <TF>` de `tv4 backtest`, valeurs `Timeframe` (`1m`, `5m`, `15m`, `30m`, `1h`, `4h`, `12h`, `1d`), défaut `1h`. Hors `config_hash` (sortie seulement) ; écrite dans `manifest.json` `outputs.equity_step`.
- En-tête `time_ms,equity,drawdown`. Format des nombres : celui de `trades.csv`.
- Échantillonnage : seau `b(j) = open_time_j.div_euclid(step_ms)` (époque Unix alignée sur 00:00 UTC, donc seaux 1h, 4h, 1d alignés UTC). Une ligne pour chaque 1m `j` de `W` qui est la dernière de son seau (dernière de la fenêtre, ou `b(j+1) ≠ b(j)`). Un seau sans aucune 1m présente ne produit pas de ligne. En `1m`, une ligne par 1m.
- `time_ms = open_time_j + 60 000` (instant du mark-to-market, jamais une borne de seau postérieure aux données) ; `equity = CellResult.equity[j − start]`.
- `drawdown` = `−dd_j` de la série **1m complète** (§2.4, pic courant depuis `initial_cash`), relevé à `j` : ≤ 0, en fraction. Il diffère donc de la série que donnerait le pic des seuls points échantillonnés ; `max_drawdown.h1` utilise, lui, le pic des points 1h.
- Ni ligne initiale au capital, ni ligne après la clôture forcée (`equity_final` est dans `metrics.json`).
- Volume : 2 ans sans heure entièrement vide = 17 520 lignes de données plus l'en-tête ; une heure Kraken sans transaction réduit ce nombre, et le warmup aussi (la fenêtre jouée commence après lui : 50 bougies 15m, soit 12 h 30, pour `sma_cross.toml`) ; écart au chiffre de l'issue attendu et documenté.
- Fonctions : `report::equity::{sample_indices, equity_csv, write_equity_csv}` ; la même `sample_indices(open_times, step)` sert à `max_drawdown.h1`.

|---|---|

## 6. `tv4 backtest` : changements de la CLI (lot A)

1. **Arguments partagés.** Les entrées du run passent dans `RunInputArgs` (`#[command(flatten)]`) : `--fixture`, `--dataset`, `--root`, `--strategy`, `--params`, `--fees`, `--fees-file`, `--instruments-file`, `--slippage-bps`, `--capital`, `--min-trades`. Une fonction `pub(super) fn prepare(args: &RunInputArgs) -> Result<PreparedRun, CliError>` rend bougies, `CellConfig` (sauf la stratégie), une fabrique de stratégie (`fn build_strategy(&self) -> Result<Box<dyn Strategy>, CliError>`, réutilisée par `tv4 bench` pour construire une stratégie fraîche par répétition), `DataInfo`, `dataset_hash`, `fixture_blake3`. `BacktestArgs` = `RunInputArgs` + `--out` + `--equity-step`.
2. `--min-trades <N>` : u32 ≥ 1, défaut 30 (`engine::DEFAULT_MIN_TRADES`) ; 0 est une erreur d'usage.
3. `--equity-step <TF>` : défaut `1h` (§4).
4. `--dataset` : une valeur sans `/`, sans `\` et sans suffixe `.json` est un **nom** (jeu `[a-z0-9_]{1,64}`, règle de `dataset build`) résolu en `<root>/datasets/<nom>.json` ; sinon un chemin, comportement S4 inchangé. Test : les deux formes donnent des `metrics.json` identiques.
5. `--out` facultatif ; défaut `<root>/runs/<run_id>` (03 §4 ; `runs/` est gitignoré). Un dossier existant est réécrit fichier par fichier, de façon atomique ; auparavant, `manifest.json` et `report.html` de l'ancien run sont supprimés (point 6).
6. Ordre : `prepare` → `run_cell` → `with_min_trades` → métriques → suppression de l'ancien `manifest.json` et de l'ancien `report.html` du dossier de sortie (absence tolérée, toute autre erreur d'E/S remonte en `ReportError::Io`) → `metrics.json` → `trades.csv` → `equity.csv` → arrêt de `cli_cold_ms` → `binary_hash` → `manifest.json`. Raison : `run_id` ne dépend ni du commit ni du binaire, donc `runs/<run_id>` est réutilisé d'un commit à l'autre ; sans cette suppression, une interruption (SIGKILL, disque plein, échec de `binary_hash`) entre deux écritures laisserait des fichiers du nouveau run sous le manifeste de l'ancien (un dossier « complet » mais incohérent, que `tv4:report` rendrait sans erreur). Une interruption ou une erreur d'écriture laisse désormais un dossier **sans manifeste**, donc non complet, jamais des fichiers du nouveau run sous l'ancien manifeste. Tests d'intégration (`tests/cli.rs`) : dossier préexistant avec `manifest.json`, `report.html` et un dossier nommé `equity.csv` → code 1, stderr cite `equity.csv`, ni `manifest.json` ni `report.html` ne subsistent, `metrics.json` et `trades.csv` du nouveau run sont présents ; réécriture réussie → ancien manifeste remplacé par un manifeste `tv4-manifest-s8` valide, `report.html` disparu.
7. Sortie standard, une ligne : `run <run_id> écrit dans <dossier> : <n> trades, PnL net <x.xx>, verdict <verdict>` (le test existant cherche `"<n> trades"`).

## 7. Changements du moteur qui alimentent les rapports (lot A)

Aucun ne change un fill, un prix, un compteur `sim` ni un `config_hash` autre que par `min_trades`.

### 7.1 `engine`

- `config.rs` : `RunConfig.min_trades: u32` ; `RunConfig::new` met `DEFAULT_MIN_TRADES = 30`. `CellConfig` **inchangé** (aucun littéral des tests ni des benches à toucher).

- `CellResult` gagne `funnel: EngineFunnel` (`evaluations`, `entry_signals`, `entry_orders`, `exit_signals`, `exit_orders`, `other_signals`, `other_accepted`, `entry_rejections: SignalRejections`, `other_rejections: SignalRejections`, `strategy: Option<StrategyFunnelCounts>`) et `bars_in_position: u64`. ### 7.2 `sim` (champs de `Trade`, sans effet sur l'exécution)

- `Trade` (Copy) : `entry_order_ms: Ts`, `exit_order_ms: Ts`, `stop_at_entry: Option<f64>`, `stop_moved: bool`.
- `Lot` : `order_ms` (= `active_from_ms` de l'ordre rempli) et `stop_at_entry` (= `self.stop` après le fill).
- `Simulator` : `stop_active_from_ms: Ts` (= `t` de la 1m de fill d'un `Enter` qui pose un stop ; = `from` d'un `MoveStop` appliqué) et `stop_moved: bool` (faux à l'ouverture de la position, vrai dès qu'un `MoveStop` est appliqué, remis à faux quand la position redevient nulle).
- `Sale` : `order_ms`, renseigné à chacune des cinq constructions (ordre en attente : `active_from_ms` ; stop : `stop_active_from_ms` ; take-profit : `tp_active_from_ms` ; clôture forcée : `end_ms`).
- Seul littéral `Trade { .. }` hors du simulateur : le test de `report/writers.rs`.

### 7.3 `strategy`

- Trait `Strategy` : `fn funnel(&self) -> Option<StrategyFunnel> { None }` (méthode par défaut, appelée hors boucle, peut allouer) ; `StrategyFunnel { raw_entry_signals: u64, filtered: Vec<(&'static str, u64)> }`.

## 10. `tv4 bench` (lot B)

`tv4 bench <RunInputArgs> [--repeat N]` (N ≥ 1, défaut 5). Rien n'est écrit sur disque.

1. Chargement une fois (`prepare`), temps de chargement affiché.
2. **Boucle** : N runs `run_cell_observed` avec un observateur chronomètre (`loop_started`/`loop_finished`, comme le bench S6) ; temps de préparation (de l'appel à `loop_started`), de boucle et de fin (de `loop_finished` au retour) ; médiane (valeur basse pour N pair) ; `ns/1m = boucle / window.bars`.
3. **`on_bar`** : N runs avec la stratégie enveloppée dans `TimedStrategy` (dans `cli/bench.rs` : délègue tout, mesure `Instant::now()` avant et après `on_bar`, cumule la durée et le nombre d'appels). La CLI a le droit de lire l'horloge, `engine` et `strategy` restent sans horloge.
4. **Surcoût du chronomètre** : 1 000 000 de paires `Instant::now()` vides, coût moyen par paire.
5. **Contrôles** : `appels == funnel.evaluations` ; `config_hash` et `n_trades` identiques entre runs enveloppés et non enveloppés (l'enveloppe délègue `id`, `version`, `params_json`). Sinon erreur.
6. **Sortie** (exemple de forme, chiffres fictifs) :

```
tv4 bench : sma_cross 1.1.0, 1051200 bougies 1m dans la fenêtre, 5 répétitions (médianes)
chargement : 312 ms
préparation : 41.0 ms (MTF et indicateurs)   boucle : 9.8 ms soit 9.3 ns/1m   fin : 0.1 ms
on_bar : 70080 appels, 61.0 ns/appel mesurés, surcoût du chronomètre 24.0 ns/appel, 37.0 ns/appel net estimé
```

Code 0. Tests (`tv4/tests/bench_cli.rs`) : sur la fixture avec `--repeat 1`, code 0, sortie contenant `ns/1m`, `ns/appel` et un nombre d'appels égal à `funnel.evaluations` d'un `backtest` identique.

### 11.2 Archivage et porte en CI, solution proposée

- Job `bench` séparé (§12), `cargo bench --locked --bench engine -- engine_2y_1m`. Le lot B vérifie que criterion 0.8.2 sans `plotters` écrit bien `target/criterion/engine_2y_1m/<fonction>/new/estimates.json`.
- Script `.github/scripts/criterion-gate.sh <estimates.json> <éléments> <seuil_ns>` (`jq` + `awk`, présents sur `ubuntu-latest`) : lit `median.point_estimate` et `median.confidence_interval.lower_bound` (ns par itération ; une itération = une boucle de n 1m), divise par n, écrit `bench-summary.json` (`{ "bench": …, "elements": n, "median_ns_per_bar": …, "lower_bound_ns_per_bar": …, "threshold_ns_per_bar": 50 }`) et échoue si `lower_bound / n ≥ 50`.
- Pourquoi la borne basse : sur un runner partagé, la médiane bouge de quelques dizaines de pour cent d'un run à l'autre ; la borne basse ne dépasse 50 ns que si même la meilleure estimation est au-dessus, c'est-à-dire une régression de l'ordre d'une allocation ou d'un hachage par bougie, ce que la porte doit attraper (03 §8). Elle ne prouve pas la performance absolue, mesurée sur le poste du propriétaire (§16).
- Artefact `criterion-engine-2y-1m` : `target/criterion/engine_2y_1m/**/new/estimates.json` et `bench-summary.json`.
- Porte bloquante (à valider) : recommandée sur la borne basse ; repli sur un job informatif (`continue-on-error: true`) si le runner s'avère trop bruité après quelques semaines.

Cet outil CLI rend un fichier à la fois : un cache compilé ne fait gagner que des millisecondes et, en prod sans `auto_reload`, faisait rendre d'anciens templates après une mise à jour du code sans rien signaler. Test : `tests/Report/TemplateFreshnessTest.php` rend un run, modifie un template dans une copie temporaire, rend avec un `Environment` neuf et vérifie que le second rendu reflète la modification.
- **Codes de sortie** : voir §14.3 ; `Tv4Application::doRun` vérifie d'abord que la commande existe (pour éviter l'invite interactive « Voulez-vous lancer X à la place ? », qui sortait en 1), puis attrape toute exception de la famille `Symfony\Component\Console\Exception\ExceptionInterface` (argument manquant, option inconnue, commande inconnue), l'affiche et sort avec 2.

- `src/Kernel.php` : `final class Kernel extends BaseKernel { use MicroKernelTrait; }` ; configuration en PHP (`config/packages/*.php`, `config/services.php`), donc pas de `symfony/yaml`.
- `config/bundles.php` : `FrameworkBundle` et `TwigBundle`, tous environnements.
- `framework.php` : `http_method_override: false`, `handle_all_throwables: true`, `test: true` en environnement `test` ; ni session, ni CSRF, ni secret si la 7.4 le permet (le secret est facultatif depuis Symfony 7.2 selon le journal des versions : **à vérifier** au premier `bin/console` ; s'il est exigé, il ne sert à rien ici et la valeur est une constante non secrète documentée comme telle, jamais une variable d'environnement ni un `.env`).
- `twig.php` : `default_path: %kernel.project_dir%/templates`, `strict_variables: true`, échappement HTML par défaut, `cache(false)`.
- `services.php` : `autowire` et `autoconfigure`, chargement de `App\` sauf `Kernel.php` et `Run/Dto/`.
- `var/cache` et `var/log` gitignorés.

### 14.3 Commande `tv4:report`

`php bin/console tv4:report <run_dir> [--output <fichier.html>]`

- Défaut de `--output` : `<run_dir>/report.html`. Écriture atomique (fichier temporaire dans le même dossier puis `rename`).
- Codes de sortie : 0 rendu écrit ; 1 run invalide (message : fichier, chemin JSON ou ligne CSV, raison) ou écriture impossible, code de la commande elle-même ; 2 erreur d'usage (argument manquant, option inconnue, commande inconnue), posé par `Tv4Application` alors que Symfony sortirait 1 : sans cela une erreur d'usage serait indiscernable d'un run invalide. Une commande future doit lever une exception ordinaire, pas une exception de la famille Console, pour un échec métier (sinon `Tv4Application` la sortirait en 2). Tests : `tests/Console/Tv4ApplicationTest.php`, via `Application::run` avec `setAutoExit(false)`.
- Syntaxe complète : `php bin/console tv4:report <run_dir> [--output <fichier.html>] [--env <env>] [--no-debug]`.
- Rendu **déterministe** : aucune date de génération, aucun chemin absolu dans le HTML ; deux rendus du même run sont identiques à l'octet (testé).

### 14.4 Lecture et validation

- `declare(strict_types=1)` partout, PSR-12, classes `final` ; DTO `final readonly class` à propriétés typées, construits seulement par le lecteur.
- Fichiers **obligatoires** : `manifest.json`, `metrics.json`, `trades.csv`, `equity.csv` (`tv4` S8 écrit toujours les quatre). Absent ou illisible → `InvalidRunException` qui nomme le fichier.
- JSON : `json_decode(…, true, 512, JSON_THROW_ON_ERROR)` ; `JsonException` traduite en « JSON invalide ». `schema` exact (`tv4-manifest-s8`, `tv4-metrics-s8`), sinon « schéma inconnu : … (attendu …) ». Accès typés par chemin (`JsonObject::string('engine.git_sha')`, `int`, `float` qui accepte un entier, `nullableFloat`, `object`, `list`) : clé absente ou mauvais type → exception avec le chemin. Clés supplémentaires tolérées (compatibilité ascendante) ; seules les clés lues sont exigées.
- CSV : en-tête **exact** (36 colonnes du §3, 3 colonnes du §4), sinon « en-tête inattendu » ; nombre de champs par ligne ; entiers par `filter_var(FILTER_VALIDATE_INT)`, flottants par motif numérique strict ; vide accepté seulement pour `stop_at_exit`, `stop_at_entry`, `risk_quote`, `r_multiple`, `regime_at_entry`, `spread_cost` ; `exit_type` dans le vocabulaire du §3.4.
- Hashes affichés **tels que `tv4` les écrit** (chaînes complètes, police à chasse fixe, coupure de ligne autorisée, jamais tronqués). Le control plane ne recalcule ni hash ni métrique.
- Mémoire : `equity.csv` en `--equity-step 1m` (≈ 1 M lignes) peut demander `php -d memory_limit=512M` ; `EquitySeries` garde trois listes scalaires, pas un objet par point.
